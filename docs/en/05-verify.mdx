The Azure and AWS offerings have different runtimes and verification paths. Use SSH, Docker, nginx, and cloud-init checks only for the Azure full-origin. The AWS offering has no SSH-accessible host and must be verified through ECS, ELB, CloudWatch, S3, network reachability, and Terraform.

## Azure full-origin verification

Quick checks run on the owned origin VM after cloud-init completes:

```bash
sudo cloud-init status --wait
curl --fail http://127.0.0.1/health
sudo nginx -t
sudo /usr/local/bin/demo-origin-ready --timeout-seconds 300
python3 /usr/local/lib/origin/application_manifest.py --manifest /opt/origin-server/applications.json --base http://127.0.0.1
```

The generated map must contain exactly nine published prefixes. `/health`, running containers and successful HTTP status are health evidence only. VAmPI returns JSON, whoami returns plain text, and every other content assertion must match the declared application identity and type.

## Complete workflow and browser verification

Use private output directories on the origin VM. Set `ORIGIN_BASE` and `EVIDENCE_DIR` to the reviewed base URL
and a fresh private evidence directory. Set `FIXTURE_INPUT` to the private JSON fixture input assembled from
actual seeded identities for `origin-verify-workflows`; it is distinct from the provisioner’s fixture
receipt/session exports. Create the output directory privately before invocation.

```bash
umask 077
sudo origin-verify-workflows \
  --manifest /opt/origin-server/applications.json \
  --fixtures "$FIXTURE_INPUT" \
  --native --require-declared --output "$EVIDENCE_DIR/native-workflows.json"
sudo origin-browser-verify content --base "$ORIGIN_BASE" --output "$EVIDENCE_DIR/content"
sudo origin-browser-verify crapi-signup --base "$ORIGIN_BASE" --output "$EVIDENCE_DIR/signup"
```

The browser wrapper supports `content`, `crapi`, `juice`, `dvwa`, `dvga`, `csd`, `restaurant`, `httpbin` and
`crapi-signup`. Native browser routing is implemented for `juice`, `dvwa`, `dvga`, `csd` and `httpbin`; use
declared native API workflows for the other applications. Repeat applicable checks on every native replica,
origin nginx, and both WAAP domains over HTTP and HTTPS. The receipt aggregator `application_receipts.py`
requires complete declared workflow/layer evidence; narrower runs cannot qualify the matrix.

Review retained PNGs and DOM/network receipts: landing inventory, same-origin navigation, static assets, lazy images, translations, console errors, forms, authenticated pages and deep-link refresh. Wrong-content 200s and missing checks fail. HTTP-only smoke tests cannot satisfy rendered review. Confirm browser/container cleanup and exact fixture restoration.

The earlier `dc99bef` matrix recorded 66 browser receipts and 315 screenshots with manual review. Later
`94cc186` signup evidence covers seven checks across native/nginx and four WAAP serving layers. Neither
qualifies all nine applications on the current PR head. [Application workflows](../application-workflows/)
explains the signup/reset journal and JWT repair. Full current-source verification, merged installation and
clean showcase rebuild remain open in [WAAP's
tracker](https://f5-sales-demo.github.io/webapp-api-protection/en/origin-traffic-remediation-tasks/).

## AWS Juice Shop Verification

Run these checks from the Terraform root that consumes `terraform/modules/aws-juice-shop`. Expose the module outputs from that root, then capture them:

```hcl
output "origin_url" {
  value = module.juice_shop.origin_url
}

output "ecs_cluster_id" {
  value = module.juice_shop.ecs_cluster_id
}

output "ecs_service_id" {
  value = module.juice_shop.ecs_service_id
}

output "target_group_arn" {
  value = module.juice_shop.target_group_arn
}
```

```bash
ORIGIN=$(terraform output -raw origin_url)
ECS_CLUSTER=$(terraform output -raw ecs_cluster_id)
ECS_SERVICE=$(terraform output -raw ecs_service_id)
TARGET_GROUP_ARN=$(terraform output -raw target_group_arn)
```

The AWS origin serves Juice Shop at `${ORIGIN}/`; `/juice-shop/`, DVGA, RESTaurant, crAPI, and every other non-Juice-Shop endpoint in this documentation require the Azure full-origin.

### Choose the HTTP execution location

Before running any AWS `curl` command, choose an execution location that can reach the configured ALB:

- **Internal ALB (default):** run from a host or runner with private DNS resolution and an implemented route into the VPC, such as VPN, Direct Connect, peering, or an F5 Distributed Cloud connected network. If F5 Distributed Cloud is the caller, its private origin connectivity must already be implemented and verified.
- **Internet-facing ALB:** run from a source included in `allowed_ingress_cidrs`. The ALB subnets must have routes to an Internet Gateway; selecting subnets in the correct VPC and Availability Zones does not make them public.

The module validates VPC and Availability Zone placement only. It does not create or validate subnet routes, gateways, VPNs, Direct Connect, peering, or F5 Distributed Cloud private connectivity.

### ECS steady state and target health

```bash
aws ecs wait services-stable --cluster "${ECS_CLUSTER}" --services "${ECS_SERVICE}"
aws ecs describe-services --cluster "${ECS_CLUSTER}" --services "${ECS_SERVICE}" \
  --query 'services[0].{desired:desiredCount,running:runningCount,pending:pendingCount,deployments:deployments[*].rolloutState}'
aws elbv2 describe-target-health --target-group-arn "${TARGET_GROUP_ARN}" \
  --query 'TargetHealthDescriptions[].TargetHealth.{state:State,reason:Reason,description:Description}'
```

The service must reach steady state with the desired task count running and every registered target reporting `healthy`.

### CloudWatch container logs

The module log group is `/ecs/<module-name>`, where `<module-name>` is the module's `name` input.

```bash
AWS_LOG_GROUP="/ecs/<module-name>"
aws logs tail "${AWS_LOG_GROUP}" --since 10m
```

Confirm recent `juice-shop` stream events exist and that there are no repeated startup failures. Do not use SSH or Docker commands: Fargate does not provide the Azure VM's container-host access model.

### ALB access logs

The caller supplies the S3 bucket and optional prefix. From the execution location selected above, generate one authorized request, then confirm that ELB log objects arrive under the regional `AWSLogs/<account-id>/elasticloadbalancing/` hierarchy beneath that prefix:

```bash
curl -sf "${ORIGIN}/" -o /dev/null -w "Juice Shop: %{http_code}\n"
aws s3api list-objects-v2 \
  --bucket "<caller-managed-alb-log-bucket>" \
  --prefix "<configured-prefix>/AWSLogs/" \
  --query 'reverse(sort_by(Contents,&LastModified))[:5].[Key,LastModified,Size]'
```

Delivery is asynchronous; retry after several minutes before treating an empty result as a failure.

### Authorized-source reachability

From the applicable execution location described above, test `${ORIGIN}/` from an address included in `allowed_ingress_cidrs`; expect HTTP `200`. Test from a controlled address outside those CIDRs; the connection must fail.

Do not make the ALB public to work around missing routing. If `public_exposure = true` is an explicit requirement, restrict `allowed_ingress_cidrs` to approved sources and verify that each selected ALB subnet routes through an Internet Gateway.
The F5 Distributed Cloud-to-ALB HTTP hop is acceptable only inside the documented trusted routing domain; use a different origin design if interception protection cannot be established.

### No-drift plan

```bash
terraform plan -detailed-exitcode
```

Exit code `0` confirms no changes. Exit code `2` means drift or unapplied configuration and must be reviewed; exit code `1` is an error.

## Azure full-origin troubleshooting

Inspect cloud-init, the private install receipt, native readiness and the exact failed workflow. Compare the
installed source/archive/manifest digests with the intended candidate. Re-run the shared installer only with
matching immutable inputs; a guest patch cannot qualify a clean rebuild. Keep failed receipts and screenshots.
Do not clear all application state, accounts or MailHog messages to recover one synthetic actor.

When using WAAP, stop traffic through `tgen-control stop` before an authorized repair window and resume through readiness-gated `tgen-control start`. Diagnose absent prerequisites separately from application rejection or WAAP mitigation.

## AWS Troubleshooting

- **ECS does not stabilize:** inspect `aws ecs describe-services` events. Verify private task-subnet DNS and HTTPS egress to Docker Hub and AWS Logs through caller-managed NAT, proxy, or equivalent endpoints.
- **Targets remain unhealthy:** inspect `describe-target-health`, ECS events, and CloudWatch logs. Confirm the image listens on `container_port`, the target-group health check reaches `/`, and the task security group allows that port only from the ALB security group.
- **CloudWatch logs are absent:** verify task egress or private endpoints, the regional Logs service principal permissions in the caller-managed KMS key policy, and the execution role's log-stream permissions.
- **ALB logs are absent:** verify the caller-managed bucket is in a supported region and its bucket policy permits regional Elastic Load Balancing log delivery to the configured prefix.
- **Internal URL is unreachable:** verify DNS, routes, and source authorization from the approved connected network. Keep the ALB internal unless public exposure is a deliberate, reviewed requirement.
- **Terraform reports changes:** review the plan against caller-managed VPC, routes, KMS, S3, provider authentication, and state. Do not apply until the ownership boundary and proposed changes are understood.
